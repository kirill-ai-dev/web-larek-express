# Пояснения к проектной работе

Этот файл помогает сопоставить текущую расширенную версию `review-admin` с тремя источниками требований:

- заданиями спринта 13;
- чек-листом перед ревью;
- тестами, которые GitHub Actions скачивает из репозитория Яндекс Практикума.

Ниже я описал найденные расхождения и то, что сделал при реализации. Где задание оставляет выбор, это указано отдельно от прямых требований.

## Откуда берутся проверки

Workflow [`.github/workflows/tests.yml`](.github/workflows/tests.yml) запускает две группы внешних проверок:

1. структурные проверки backend;
2. Newman-коллекцию `sprint-13.json` через Docker и nginx.

Коллекция проверяет базовые маршруты спринта. Расширенные сценарии авторизации и загрузки файлов дополнительно покрыты тестами в `backend/tests/`; они запускаются локально и отдельным заданием GitHub Actions с MongoDB.

Сравнение выполнено 17 ноября 2026 года по проверенной версии внешних тестов: [`49125c71712ae49438c85f44b0f07908a40a4c73`](https://github.com/Yandex-Practicum/tests-web-larek-express/tree/49125c71712ae49438c85f44b0f07908a40a4c73). Коллекция находится в [`collections/sprint-13.json`](https://github.com/Yandex-Practicum/tests-web-larek-express/blob/49125c71712ae49438c85f44b0f07908a40a4c73/collections/sprint-13.json). Workflow скачивает актуальную версию при каждом запуске, поэтому внешние тесты могут меняться независимо от проекта.

Файлы `backend/tests/auth.test.cjs`, `backend/tests/password.test.cjs` и `backend/tests/products.test.cjs` добавлены в ходе разработки. Это отдельный набор на `node:test`, которого не было в шаблоне. API-тесты используют временные базы MongoDB и папки, а тесты хеширования проверяют функции без обращения к базе. Успех этих проверок не означает автоматический успех внешней коллекции.

## Статус создания товара и зависимости

В шаге 2 описан ответ созданного товара, но успешный HTTP-код отдельно не указан. Внешняя коллекция явно ожидает 201. Поэтому я заменил первоначальный ответ 200 на `res.status(201).send(product)`.

В шаблоне были зависимости, которые первоначальная реализация не использовала. Внешняя структурная проверка запрещает лишние production-зависимости. Я убрал неиспользуемые `validator`, `@types/validator` и отдельный `joi`: Joi импортируется из `celebrate`. После добавления пользователя email на уровне модели проверяется регулярным выражением, что разрешено чек-листом; возвращать `validator` для этого не потребовалось.

## Разногласия между базовыми тестами и шагами 7–8

В запросах создания товара из внешней коллекции используется следующий объект `image`:

```json
{
  "fileName": "/images/image.png",
  "originalName": "image.png"
}
```

В коллекции нет предварительной загрузки этого файла, а в стартовом проекте такого пользовательского файла нет. Она также отправляет `POST /product` без access-токена.

Шаг 7 предусматривает загрузку и перенос настоящего файла, а шаг 8 требует авторизацию. В расширенной версии я реализовал следующий порядок:

- новый файл сначала передаётся в `POST /upload`, а полученный объект — в JSON товара; уже сохранённую картинку можно использовать повторно;
- путь картинки должен указывать на существующий временный или постоянный файл; если файла нет, я выбрал ответ 400, чтобы не сохранять заведомо неработающий путь;
- `POST /product`, `PATCH /product/:productId`, `DELETE /product/:productId`, `POST /upload` и `GET /auth/user` защищены авторизацией;
- отсутствие или неверность токена возвращает 401 до обработки данных товара и записи файла.

Я сохранил защиту из шага 8 и проверку наличия картинки. Поэтому запрос базовой коллекции без токена получает 401. Если добавить токен, но оставить отсутствующий файл, он получит 400. Чтобы проверить успешное создание в расширенной версии, нужны авторизация и реальная картинка.

Для расширенной версии workflow запускает [подготовку коллекции](.github/scripts/prepare-api-collection.cjs): через API регистрирует временного пользователя, загружает настоящую картинку и создаёт временную копию скачанной коллекции. В POST-запросы товара добавляется Bearer-токен, а `/images/image.png` заменяется путём загрузки. Исходные запросы, ожидаемые коды и все проверки ответов сохраняются. GET каталога и оформление заказа остаются без авторизации. Перед подготовкой отдельно проверяется 401 для создания товара без токена.

Это адаптация окружения базовых тестов к расширенной работе. Защита API не отключается, проверки не пропускаются, исходный репозиторий тестов не изменяется. Сценарии отказа без токена, отсутствующего файла, редактирования, удаления и авторизации также проверяются набором `backend/tests/` в CI.

## Цена из формы админки

В задании цена — число или `null`, но готовая форма админки передаёт введённую цену строкой. Я разрешил преобразование только `price` в POST и PATCH: например, `"1234"` превращается в `1234`. В MongoDB и ответе API цена остаётся числом или `null`. Нечисловые строки, пустая строка, массивы и объекты отклоняются; остальные поля проходят строгую проверку без преобразования типов. Форму frontend для этого не менял.

## Форматы изображений

Шаг 7 требует ограничить размер и типы, но не задаёт точные значения. В чек-листе список уточнён: `image/png`, `image/jpg`, `image/jpeg`, `image/gif`, `image/svg+xml`. Я привёл загрузку ко всему списку из чек-листа. Ранее использовавшееся ограничение PNG/JPEG больше не действует. Лимит 5 МБ — выбранная настройка, а не число из условия. Имя файла генерируется на сервере; оба JPEG MIME-типа сохраняются с расширением `.jpg`.

Для PNG, JPEG и GIF проверяется сигнатура файла. SVG разбирается как XML; запрещены скрипты, CSS, анимации, обработчики событий, внешние ссылки, `foreignObject`, DOCTYPE и повреждённый XML. Стартовые SVG-файлы проходят эту проверку.

SVG поддерживается как статичное изображение: фигуры, текст, фильтры и внутренние ссылки. Это дополнительное ограничение содержимого, выбранное мной; задание требует поддержку SVG, но не описывает обработку активного содержимого.

Пути папок берутся из `UPLOAD_PATH` и `UPLOAD_PATH_TEMP`. Временная папка не раздаётся через HTTP. После записи товара временный оригинал удаляется. Хук модели удаляет картинку при удалении товара, если другие товары на неё не ссылаются. Для забытых загрузок я выбрал очистку через `cron` раз в час с удалением файлов старше суток; в задании точный интервал не указан.

## Авторизация и payload токена

Access-токен по умолчанию действует 10 минут, refresh-токен — 7 дней; сроки берутся из `.env`. Refresh-токен хранится в httpOnly-cookie и заменяется при обновлении сессии. Пароль я хеширую встроенной функцией `scrypt` со случайной солью. Задание требует хеш, но не устанавливает конкретный алгоритм. `password` и `tokens` имеют `select: false` и не возвращаются клиенту.

После проверки JWT middleware записывает payload в типизированное поле `req.user`. В payload сохраняется `_id` пользователя, а также стандартные `iat` и `exp`, добавленные JWT-библиотекой.

В шаге 6 сказано передавать в payload только `_id`. Из пользовательских данных я добавляю только `_id`; стандартные `iat` и `exp` нужны для срока действия JWT. Чек-лист упоминает `middlewares/auth.js`, но проект написан на TypeScript: исходник — `backend/src/middlewares/auth.ts`, файл `.js` появляется в `dist` после сборки.

Секреты подписи читаются из `.env`, а не хранятся в репозитории. В `.env.example` ключи перечислены, значения нужно сгенерировать по инструкции backend README. Для Docker-проверки в CI [отдельный скрипт](.github/scripts/prepare-ci-env.cjs) копирует примеры окружения, генерирует случайные секреты текущего запуска и устанавливает адрес MongoDB внутри Docker. Файлы с секретами и подготовленная коллекция не добавляются в Git и артефакты.

## Валидация и обновление товара

Тела запросов, ID товара и заголовок `Authorization` проверяются через `celebrate` до контроллеров. Я убрал явные вызовы `product.validate()` из контроллеров, чтобы не дублировать входную валидацию. Проверка MongoDB-схемы остаётся на уровне Mongoose при сохранении и обновлении. Проверка наличия товара, суммы заказа и файла относится к работе с данными и остаётся в соответствующей логике.

Чек-лист требует `{ runValidators: true, new: true }`. Раньше я использовал `new: false`, получал фактически заменённую картинку и собирал обновлённый ответ. Теперь PATCH возвращает обновлённый документ через `new: true`. Чтобы сохранить очистку картинок при параллельных запросах, я добавил очередь PATCH и DELETE одного товара внутри процесса сервера. Для нескольких процессов сервера эта очередь не является общей — такой запуск здесь не реализован. Обновления пользовательских токенов также используют `runValidators`; `new: true` задан там, где метод возвращает документ.

При отсутствии картинки во временной и постоянной папках сервер возвращает 400. При ошибке сохранения новая постоянная копия удаляется, а временный файл остаётся для повторной попытки.

## Ответы и ошибки

Ошибки контроллеров передаются через `next` в единую middleware и возвращаются в формате `{ "message": "..." }` с подходящим кодом 400, 401, 404, 409 или 500. Ошибки до контроллера обрабатывает `celebrate.errors()`; формат celebrate сохранён, как разрешено шагом 3.

Для `/auth/token` удалённый пользователь даёт 404 согласно итоговой таблице маршрутов, а завершённая сессия существующего пользователя — 401.

## Локальный запуск и Docker

Backend работает на порте из `.env`; при локальной проверке frontend использует `VITE_API_ORIGIN=http://localhost:3000`. Внешняя коллекция использует `http://localhost/api` — адрес nginx из Docker-инфраструктуры. Префикс `/api` обрабатывается nginx и не добавляется к Express-маршрутам.

Docker Compose оставлен из шаблона. Ранее предложенную настройку healthcheck в него не включал. Полный запуск расширенной версии через Compose проверен из отдельной чистой копии: frontend, backend, MongoDB и nginx. Тестовые порты отличались от рабочих, чтобы не останавливать локальный сервер. После запуска API прошёл коллекцию Newman через nginx.

В GitHub отдельный job `test_extended_api` использует свой MongoDB-контейнер и ждёт его готовности до тестов. Это окружение CI, не изменение запуска проекта в Compose. Для Newman оставлен Node.js 18 из шаблонного workflow: старый Newman 5.3.2 несовместим с установленным локально Node.js 24.

## Логи

`requestLogger` подключён до роутов, `errorLogger` — после роутов и до обработчиков ошибок. Логи сохраняются в JSON. В `request.log` записываются сведения о запросе, статус ответа и время обработки. Тела ответов целиком не сохраняются: они могут содержать access-токен. Пароли, заголовки Authorization и cookie также не записываются. Файлы логов исключены из Git.
